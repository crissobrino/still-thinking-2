## Overview

This document describes, in full, the evaluation strategy undertaken for the Still Thinking pipeline — what was tried, why certain approaches were aborted or redesigned, and what the final rounds measured and produced. The evaluation covers two distinct axes: (1) **retrieval quality** (how well ChromaDB retrieves relevant papers), and (2) **generation quality** (how well the LLM compares the user's idea against retrieved papers). Both axes were evaluated with and without a CrossEncoder reranker, and across two LLM sizes: `qwen3:8b` (small) and `qwen3:32b` (large).

---

## Part 1 — Retrieval Quality Evaluation

### 1.1 What was measured

Three retrieval configurations were benchmarked:

| Config | Description |
|--------|-------------|
| **ANN** | Approximate nearest neighbour via ChromaDB cosine similarity, top-5 |
| **ANN + Rerank** | Fetch top-20 via ANN, re-rank with `ms-marco-MiniLM-L-6-v2` CrossEncoder, keep top-5 |
| **ENN** | Exact nearest neighbour (brute-force) — used as gold standard |

Metrics used:
- **Precision@5 (score-based):** fraction of top-5 results with cosine similarity ≥ 0.35.
- **Precision@5 (overlap):** fraction of ANN/Rerank results that also appear in the ENN gold set.
- **NDCG@5:** Normalised Discounted Cumulative Gain at rank 5, measuring ranking quality against the gold standard.
- **MRR:** Mean Reciprocal Rank — how highly the first relevant result is ranked.
- **Latency:** total wall-clock time per query, in milliseconds.

### 1.2 Test query set

The gold standard was generated by `generate_gold.py` using the ENN+Rerank configuration. The evaluation queries (`test_queries.json`, 7 queries; `evaluate_precision.py` uses 10) cover:

- **On-topic NLP/Healthcare** (e.g., "transformer architectures for medical image segmentation", "federated learning for clinical data privacy", "biomedical NER with LLMs", "GNNs for drug-target interaction", "attention mechanisms for protein structure prediction")
- **Borderline** (e.g., "deep learning applications in healthcare")
- **Multilingual** (e.g., "aprendizaje automático para clasificación de texto clínico")
- **Off-domain** (e.g., "quantum computing error correction", "history of the Roman Empire")

Off-domain queries are essential to test the **guardrail** — the system should refuse to answer rather than hallucinate.

### 1.3 Scripts

| Script | Purpose |
|--------|---------|
| `evaluate_precision.py` | Computes Precision@K (score-based + overlap) for ANN, ANN+Rerank, ENN |
| `main_eval.py` | NDCG@5 killer chart with 95% CI error bars, latency–quality scatter |
| `main_eval_mrr.py` | Adds MRR; produces separate NDCG and MRR killer charts |
| `evaluation_rag.py` | Comprehensive comparison table: Precision@5, MRR, NDCG@5 per config |
| `ablation.py` | Ablation: ANN vs ANN+Rerank vs ENN, NDCG + latency |
| `generate_gold.py` | Generates `gold_standard.json` using max config (ENN + Rerank) |
| `evaluation_utils.py` | Shared NDCG, MRR implementations and API call helpers |

### 1.4 Guardrail evaluation

`advanced_eval.py` builds a confusion matrix for the guardrail (should_refuse). It classifies 14 queries — 10 on-topic (NLP/healthcare) and 4 off-domain (cooking, maths integrals, mountain hiking in French, Roman history) — and measures how accurately the system accepts vs. refuses each. The guardrail threshold is cosine similarity ≥ 0.05; if no retrieved result clears this, the system returns a canned refusal instead of calling the LLM.

## Part 2 — Generation Quality: The RAGAS Journey

This is where the most iterations happened. The goal was to evaluate whether the LLM's comparative responses were (a) faithful to the retrieved context, (b) relevant to the user's research query, (c) precise in using retrieved context, and (d) recalled the gold standard information. What follows is the **chronological account of every judge model tried**, why each was abandoned, and what ultimately worked.

### 2.0a Attempt 1 — Groq + Llama-3.3-70b (April 25, commit "grok funciona")

The very first attempt used the Groq API (`console.groq.com`) with a redirected OpenAI client pointing at `https://api.groq.com/openai/v1`. The judge model was **Llama-3.3-70b-versatile**, a large open-source model available for free on Groq's infrastructure.

**What it did:** `evaluate_grok.py` and `evaluate_grok2.py` both used hardcoded test data — manually written questions, contexts, and answers about transformer applications in cancer detection and bioinformatics. They did not call the Still Thinking pipeline at all; the data was embedded directly in the script.

**Why it was abandoned:** It was a prototype to confirm that RAGAS could be wired to a non-OpenAI judge via the OpenAI-compatible interface. It produced correct faithfulness scores on the static data. However, the script was not integrated with the pipeline or the test_queries.json test set, the API key was hardcoded in plaintext in the source, and Groq's free tier rate limits would not support the full evaluation loop. It was a proof-of-concept, not a production evaluator.

---

### 2.0b Attempt 2 — qwen3 self-evaluation (`evaluate_automated.py`)

The first real pipeline-integrated evaluator used the same **UC3M Ollama server** for both the generation model and the RAGAS judge. The pipeline ran qwen3:8b or qwen3:32b to generate answers, and the judge was also qwen3:8b or qwen3:32b via the UC3M `/v1` OpenAI-compatible endpoint.

**Why it was abandoned:** Self-evaluation bias. A model judging its own outputs is not a sound methodology — qwen3 would be evaluating whether its own generation is "faithful" to context, which consistently inflated faithfulness scores. RAGAS also struggled with the UC3M server's latency (the shared GPU server is under load and has read timeouts through nginx), causing frequent `ReadTimeout` exceptions mid-evaluation. The LangchainLLMWrapper retry logic was insufficient to handle the server's intermittent unavailability.

---

### 2.0c Attempt 3 — Different-family judge: gemma2:9b and llama4:16x17b (`evaluate_automated2.py`)

To eliminate self-evaluation bias, the pipeline model was fixed to **qwen3:8b** and the judge was switched to a completely different model family: **gemma2:9b** (fast) or **llama4:16x17b** (strong), both served via the same UC3M Ollama server.

**Why it was abandoned:** The UC3M server's intermittent availability remained the core issue — RAGAS calls to the judge would timeout partway through the evaluation loop, and the incremental save logic was not yet in place (that came later). Additionally, `llama4:16x17b` was too slow on the shared GPU server to be practical for a 7-query evaluation loop. `gemma2:9b` was faster but its RAGAS faithfulness outputs were inconsistently formatted, causing parse failures in the RAGAS verdict extraction logic.

---

### 2.0d Attempt 4 — llama3.1:8b pipeline + gemma2:9b judge (`evaluate_automated3.py`)

The pipeline model was switched to **llama3.1:8b** and the judge remained **gemma2:9b**, both on UC3M. The rationale was that llama3.1:8b is a lighter model that generates faster, reducing total wall-clock time.

**Why it was abandoned:** llama3.1:8b produced noticeably weaker structured comparisons than qwen3 — the five-section format (research direction, relevant articles, key differences, novelty, conclusion) was often incomplete or inconsistently formatted. The `<b>` and `<ul>` HTML markup requested by the prompt template was frequently missing or malformed. The combination of a weaker generator and the UC3M judge latency issues meant this attempt produced neither fast nor high-quality results. The gemma faithfulness results from this run are preserved in the git history (`evaluation/automated_results_gemma_faithfulness.csv`, committed in "gemini last try and specter db") but are not considered reliable enough to report.

---

### 2.0e Attempt 5 — Gemini 2.0 Flash-Lite as judge (`evaluate_gemini.py`, commit "gemini last try", May 2)

A new approach: keep the pipeline on **llama3.1:8b** (UC3M) but move the RAGAS judge to **Gemini 2.0 Flash-Lite** via Google's Generative Language API (`langchain_google_genai`). Gemini Flash-Lite is fast and cheap — a reasonable judge candidate.

**Why it was abandoned:** The RAGAS LangchainLLMWrapper's verdict extraction relies on the judge LLM producing structured JSON in a very specific format. Gemini 2.0 Flash-Lite returned correctly reasoned answers but wrapped them in markdown code fences and with slight variations in key names that RAGAS could not parse reliably. The faithfulness metric produced `NaN` scores for most queries. The commit message "gemini last try" captures the frustration — this was the point at which the decision was made to abandon UC3M-hosted judges entirely and move to a commercial API with reliable output formatting.

---

### 2.0f Attempt 6 — Manual qwen3:32b judge (`evaluate_manual.py`)

Before committing to OpenAI, one more attempt was made using **qwen3:32b** as a manual (non-RAGAS) judge via the native Ollama API on UC3M. The idea was to call the judge directly and parse its structured output, bypassing RAGAS's fragile LangchainLLMWrapper entirely.

**Why it was abandoned:** The UC3M server latency remained problematic for a 7-query × 3-retry loop. More critically, the `<think>...</think>` contamination issue had not yet been diagnosed — qwen3:32b's internal chain-of-thought was appearing in the judge responses and breaking the score extraction regex. This was the experiment that uncovered the think-block problem, which was then fixed globally in all subsequent scripts.

---

### 2.0g Final approach — GPT-4o-mini via OpenAI API

After five failed judge backends, the decision was made to use **GPT-4o-mini via the OpenAI API**. This resolved every infrastructure problem at once: reliable JSON output formatting, no server timeouts, and a model completely independent from the qwen3 pipeline. The cost per evaluation run is low enough ($<$0.10 for the full 7-query set) to be acceptable. This is what `evaluate_openai.py` (RAGAS metrics) and `evaluate_manual_openai.py` (custom rubric) use.

---

### 2.1 Why standard RAGAS is still a poor fit for this task (even with GPT-4o-mini)

Still Thinking is **not a factual QA system**. Standard RAGAS was designed for QA pipelines where:
- The question has a single factual answer.
- The "ground truth" is a short, specific statement.
- Context relevance is judged by whether the context contains the answer.

Still Thinking is a **comparative analysis system**: the user submits a research idea, the system retrieves tangentially related papers, and the LLM synthesises a structured comparison across five sections (research direction, relevant articles, key differences, possible novelty, conclusion). This introduces several fundamental metric compatibility issues that caused early evaluation runs to produce misleading scores.

---

### 2.2 Problem 1 — Context Precision: permanently broken (all zeros)

**What happened:** Every single query in both the small and large model runs returned a Context Precision score of **0.000**. No exceptions.

**Root cause:** RAGAS's Context Precision metric determines whether each context chunk is "useful" for producing the ground truth answer by asking the judge LLM to verify whether the chunk would help a reader arrive at the ground truth. The ground truths used here are short domain-knowledge statements written by a human (e.g., *"Federated learning allows training ML models across decentralised clinical datasets without sharing raw patient data…"*). The retrieved context chunks are paper abstracts from ChromaDB. These abstracts do not contain — and were never intended to contain — the exact domain knowledge in the ground truth. They are papers retrieved by semantic similarity to the query, which in many test cases are only loosely related.

The judge correctly and consistently responds: "this abstract does not help me arrive at the ground truth." It is right. But this reflects a **test design mismatch**, not a system failure.

**Decision:** Context Precision was retained in the small-model results file for completeness but is not reported as a meaningful metric and was dropped from all subsequent analysis. The metric is structurally incompatible with this task.

---

### 2.3 Problem 2 — Faithfulness: false positives on comparative statements

**What happened:** The faithfulness metric initially flagged comparative statements like *"the user's research idea differs from Article X"* as hallucinations, because these statements cannot be verified from the context chunks alone — they reference the user's query, which is not part of the context.

**Root cause:** RAGAS Faithfulness decomposes the answer into atomic statements, then checks whether each is supported by the provided context. Comparative statements that reference the user's original query are not supported by any retrieved abstract. RAGAS correctly marks them as unsupported, but these statements are legitimate conclusions — they're not hallucinations.

**Fix:** The user's query was prepended as an explicit context item (`"User research query: {q}"`) before the list of abstracts. This gives the faithfulness judge a grounding for comparative statements without altering the retrieval pipeline. This is why the faithfulness scores ended up at 0.90–1.00 rather than being artificially depressed.

**Evidence from results:** The one case where faithfulness dropped below 1.0 was the Spanish query ("aprendizaje automático para clasificación de texto clínico"), which scored 0.667. Inspecting the verdict breakdown: the three statements marked with `verdict: 0` were all ones where the answer referenced the user's research focus ("focuses on specific clinical text", "does not mention specific methods", "does not specify the use of structured data") — meta-statements about what the query says rather than what the context says. These are genuinely hard to ground even with the query prepended as context.

---

### 2.4 Problem 3 — Answer Relevancy via RAGAS: breaks for research ideas

**What happened:** The RAGAS `AnswerRelevancy` metric computes relevance by:
1. Generating several questions that the answer could be a response to.
2. Measuring the semantic similarity between these generated questions and the original input question.

For a bare research topic like *"attention mechanisms for protein structure prediction"*, the generated questions from the answer tended to be phrased like *"What are the key differences between attention-based models and retrieved NLP papers?"* — semantically distant from the short bare topic. This produced artificially low relevance scores.

**Fix:** The question was expanded before passing to RAGAS to explicitly encode the task structure:

```python
full_question = (
    f"Given the research idea '{q}', compare it with retrieved academic articles: "
    f"identify what each article covers, highlight key differences between the idea "
    f"and the existing works, and assess possible novelty."
)
```

This expansion ensures the RAGAS-generated reverse questions are semantically close to the expanded form. The answer relevancy scores after this fix reached 0.82–1.00 across the test set.

**However**, this RAGAS-based answer_relevancy has a second limitation: it measures *embedding similarity* between the original (expanded) question and the reversed questions, which is a proxy measure. It cannot judge whether the response actually covers the five required sections with appropriate depth. This led to the development of the manual judge.

---

### 2.5 Problem 4 — Qwen3 think-block contamination

**What happened:** Qwen3 (both 8b and 32b) occasionally emits a `<think>...</think>` block before the actual answer — this is the model's internal chain-of-thought reasoning, which appeared in the raw responses stored in the pipeline cache.

**Fix:** A regex stripping step was added before any evaluation:

```python
collected["answer"] = [
    re.sub(r'<think>.*?</think>', '', a, flags=re.DOTALL).strip()
    for a in collected["answer"]
]
```

This is applied in both `evaluate_openai.py` and `evaluate_manual_openai.py`.

---

### 2.6 Solution: manual LLM-as-a-judge with a bespoke rubric

The RAGAS answer relevancy, even after question expansion, was measuring the wrong thing for the final two sections (novelty and conclusion depth). A fully custom judge was built in `evaluate_manual_openai.py` using GPT-4o-mini as the judge, with a bespoke scoring rubric in `prompts/answer_relevancy_system.txt`.

**Rubric structure:** The judge rates five sections individually on a 0–10 scale and computes a normalised total:

```
Research direction:  0–10 (Is the user's topic correctly restated?)
Relevant articles:   0–10 (Are retrieved articles described relative to the query?)
Key differences:     0–10 (Are differences between the idea and articles addressed?)
Possible novelty:    0–10 (Is novelty assessed, even cautiously?)
Conclusion:          0–10 (Is a conclusion provided?)

SCORE = total / 50
```

**Critical design decision in the system prompt:** The judge was explicitly instructed:
> *"An answer that correctly identifies the lack of overlap and says 'insufficient context' is a PERFECT response and must score highly. Never dock points because articles don't match the query. Do NOT penalize for hedging language."*

This was necessary because the retrieval system will sometimes surface papers with low topical overlap (e.g., the query "GNNs for drug-target interaction" returned papers on toxicology, emotion modelling, and technology forecasting). The LLM correctly identifies this mismatch and responds with appropriate epistemic humility ("novelty cannot be assessed due to insufficient context"). Without this instruction, an evaluator LLM would penalise exactly the correct behaviour.

## Part 4 — What Was Abandoned and Why

### 4.1 Context Precision as a metric

Fully abandoned from final reporting. The metric is structurally incompatible with this use case (see §2.2). It would only be meaningful if the ground truths were excerpts from the retrieved papers themselves — which would require a different evaluation design.

### 4.2 Vanilla RAGAS Answer Relevancy (without question expansion)

Abandoned. Produces unrealistically low scores because RAGAS's reverse-question generation from comparative answers produces semantically distant questions when compared to short bare topic strings. Replaced with: (a) question expansion for the RAGAS-based metric, and (b) the fully manual judge as the primary metric.

### 4.3 Evaluation without the query-as-context trick

Abandoned. Without prepending the user query as a context item, faithfulness scores are artificially depressed by 15–30 percentage points on comparative queries. All final runs include this fix.

### 4.4 Batch evaluation (all queries in one RAGAS call)

Abandoned in favour of query-by-query evaluation with incremental CSV saving. The RAGAS judge (GPT-4o-mini) has a per-minute rate limit and can time out on large batches. Incremental saving means a crash at query 5 of 7 doesn't lose all previous work.

## Part 6 — Key Takeaways

1. **RAGAS is not plug-and-play for comparative RAG.** The three issues (context precision, faithfulness on comparative statements, answer relevancy for topic queries) all required custom fixes. In retrospect, a fully manual rubric-based judge was always going to be more reliable for this task structure.

2. **The manual 5-section rubric is the most meaningful metric.** It directly reflects what the system is supposed to do (restate the query, describe articles, identify differences, assess novelty, conclude), and the judge instructions explicitly handle the case where retrieval quality is poor — which is common when querying a domain-specific corpus with out-of-distribution ideas.

3. **The Spanish query is the hardest case across every dimension.** Faithfulness, context recall, and answer relevancy all dipped relative to the English queries. The multilingual path (detect → translate → retrieve → respond in original language) introduces additional failure modes: translation distortion, retrieval in a language that doesn't match the paper corpus, and gold standard mismatch.

4. **Reranking helps retrieval but doesn't fully fix domain gaps.** Several queries (GNNs, protein structure) retrieved papers with very low topical overlap regardless of reranking. The system behaves correctly in these cases (identifies the mismatch), but the retrieval itself is the bottleneck, not the LLM.

5. **Pipeline caching was essential.** Generating responses from qwen3:32b takes several minutes per query. Running the pipeline once and caching the outputs allowed rapid metric iteration without re-running the expensive generation step.
